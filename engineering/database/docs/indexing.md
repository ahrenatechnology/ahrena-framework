# When and Which Indexes, Within the Database's Premises

This is the rationale behind [`rules/index-coverage.md`](../rules/index-coverage.md). An index is a trade: every read it serves gets faster, and every write to the table pays to keep it. So an index exists because a named query needs it, and leaves when no query does. Where that query comes from depends on the kind of database, and the two kinds are argued separately because their premises differ.

## Relational: the index follows the query

In PostgreSQL, SQLite and MySQL the schema is designed from the entities, and the indexes are added from the queries the adapters run. The procedure is the same on all three: list each query an adapter issues, with its filter, join and sort columns; give it an index whose leading columns are the ones it filters on by equality; read the plan to confirm the index is used; and drop the indexes no query uses.

**Read the plan, do not guess it.** The database says how it will run a query: `EXPLAIN` in PostgreSQL shows a `Seq Scan` where it reads the whole table and an `Index Scan`, `Index Only Scan` or `Bitmap Heap Scan` where an index serves it, and `EXPLAIN ANALYZE` actually executes the statement ([PostgreSQL: Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html#USING-EXPLAIN-ANALYZE)). SQLite's `EXPLAIN QUERY PLAN` says `SCAN` for a full table scan and `SEARCH ... USING INDEX` when only a subset of rows is visited ([EXPLAIN QUERY PLAN](https://sqlite.org/eqp.html#table_and_index_scans)). MySQL's `EXPLAIN` reports join type `ALL` for a full table scan ([EXPLAIN Output Format](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html#jointype_all)). An integration test that runs the adapter's query against a table with rows in it, and asserts the plan, is the detector; a planner may choose a scan on an empty table, so the test seeds enough rows that a scan is the worse plan.

**Column order.** A multicolumn B-tree index is most efficient when the query constrains its leading, leftmost columns ([PostgreSQL: Multicolumn Indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html)). Equality columns go first, then the sort or range column.

**Foreign keys.** PostgreSQL does not create an index on the referencing columns of a foreign key ([Foreign Keys](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK)); a join or a cascade along it then scans, so the design adds one when a query joins or deletes along the key. MySQL requires an index on the referencing columns and creates it if none exists ([FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html#foreign-key-restrictions)).

**Narrower indexes.** A partial index covers only the rows a query reads, such as the open orders ([PostgreSQL: Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html), [SQLite: Partial Indexes](https://sqlite.org/partialindex.html)). An expression index serves a query that filters on a computed value, including a field inside JSON ([PostgreSQL: Indexes on Expressions](https://www.postgresql.org/docs/current/indexes-expressional.html), [SQLite: Indexes On Expressions](https://sqlite.org/expridx.html#how_to_use_indexes_on_expressions), [MySQL: functional key parts](https://dev.mysql.com/doc/refman/8.4/en/create-index.html#create-index-functional-key-parts)). A `jsonb` column that is searched by containment takes a GIN index ([jsonb Indexing](https://www.postgresql.org/docs/current/datatype-json.html#JSON-INDEXING)); a JSON array in MySQL takes a multi-valued index ([multi-valued indexes](https://dev.mysql.com/doc/refman/8.4/en/create-index.html#create-index-multi-valued)).

**Unused indexes.** PostgreSQL counts the scans started on each index in `pg_stat_user_indexes.idx_scan` ([Cumulative Statistics](https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-ALL-INDEXES-VIEW)); MySQL lists them in `sys.schema_unused_indexes` ([sys schema](https://dev.mysql.com/doc/refman/8.4/en/sys-schema-unused-indexes.html)). Both count since the statistics were last reset, so a zero read the day after a restart is not evidence. In review, the cross-check is static: each index in the migrations is matched to a query in the adapters that the plan shows using it.

## NoSQL: the access patterns come before the schema

In MongoDB and DynamoDB the order is reversed. AWS states it plainly for DynamoDB: "you shouldn't start designing your schema until you know the questions that it needs to answer" ([NoSQL design for DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-modeling-nosql.html)). So the design first lists every access pattern — who reads or writes what, by which key, in which order, how often — and the keys and indexes are drawn from that list. A pattern that arrives later is a new index, or a new item shape, decided against the list.

**DynamoDB.** The partition key spreads the load: the more distinct partition key values a workload touches, the more evenly its requests spread ([Designing partition keys to distribute your workload](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-uniform-load.html)). The sort key orders the items of one partition and serves range reads and version prefixes ([sort keys](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-sort-keys.html)). A local secondary index can only be created with the table, allows strongly consistent reads, and caps each item collection at 10 GB ([Local secondary indexes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/LSI.html)); a global secondary index can be added later, backfills while the table stays available, and is read eventually consistent ([GSI writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.html#GSI.Writes), [Adding a GSI to an existing table](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.OnlineOps.html#GSI.OnlineOps.Creating.Phases)). A `Scan` reads the entire table or index ([Querying and scanning](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-query-scan.html#bp-query-scan-performance)), so an access pattern served by a scan is a missing key. Whether one table or several hold the items depends on how the access patterns correlate; AWS's guide lists single-table, multi-table and aggregate designs and does not make single-table a rule ([NoSQL design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-modeling-nosql.html)).

**MongoDB.** A compound index puts equality fields first, then sort fields, then range fields — the Equality, Sort, Range guideline ([ESR](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/)). `explain()` shows a `COLLSCAN` stage for a collection scan and `IXSCAN` for an index, and `totalDocsExamined` against `nReturned` says how much was read to answer ([Explain Results](https://www.mongodb.com/docs/manual/reference/explain-results/)). `$indexStats` reports each index's use; its counters reset when the server restarts, so a zero is read against `accesses.since` ([$indexStats](https://www.mongodb.com/docs/manual/reference/operator/aggregation/indexStats/)). The model is shaped by the access patterns too: data read together is embedded, within the document limit ([Limits](https://www.mongodb.com/docs/manual/reference/limits/)).

The access patterns are recorded in the mode registry with the table they belong to ([`entity-history.md`](entity-history.md)), so the keys can be checked against them.

## Shipping a new index without locking writes

A plain `CREATE INDEX` in PostgreSQL locks out writes, not reads, until it is done; `CREATE INDEX CONCURRENTLY` does not, at the cost of two table scans, and it cannot run inside a transaction block. A concurrent build that fails leaves an `INVALID` index behind, to be dropped and built again ([Building Indexes Concurrently](https://www.postgresql.org/docs/current/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)). The migration that builds it is therefore its own migration, marked by the migration tool as running outside a transaction.

MySQL builds a secondary index in place and the table stays available for reads and writes ([Online DDL index operations](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html#online-ddl-index-operations)); the migration states `LOCK=NONE`, which makes MySQL halt with an error rather than build with less concurrency than asked ([ALTER TABLE — Concurrency Control](https://dev.mysql.com/doc/refman/8.4/en/alter-table.html#alter-table-concurrency)). MongoDB builds an index holding an exclusive lock on the collection only briefly at the beginning and end ([Index Builds on Populated Collections](https://www.mongodb.com/docs/manual/core/index-creation/)). A DynamoDB global secondary index backfills online, and cannot be queried until it is `ACTIVE`. SQLite allows one writer at a time ([WAL — concurrency](https://sqlite.org/wal.html#concurrency)), so an index build on a SQLite table holds the write lock for its duration; the design states that the table is small enough, or that the build runs in a maintenance window.

Which tables need this care is not a row count invented here: a table that already holds rows in an environment people use is built without locking writes; a table created in the same migration is not, because nothing writes to it yet.

## Where this stops

This page decides which indexes exist and how they ship. Query tuning beyond the index — rewriting a query, changing a join, caching a result — is the builder's, and a slow query in production is diagnosed by `skills/diagnosing-database/SKILL.md`. Search indexes (full text, vectors) are a choice of service, made in the design with the cloud plugin.
