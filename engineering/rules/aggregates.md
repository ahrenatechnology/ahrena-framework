# The aggregate boundary and the event that leaves it

Six conditions. Each names a detectable state and what decides it, and every one of those detectors needs a marker the consuming project supplies: which type is an aggregate root, which is an event, which function is a use case. The final section says why that makes this a judgment rule and what the judgment costs. `docs/aggregates.md` explains what each condition protects, where the two figures came from, and the cases where enlarging a boundary is the right answer.

**This is the modelling vocabulary, on top of a layout that already exists.** `rules/domain-model.md` declares where a context lives, what a domain module may import, what an aggregate root must carry and how a persisted entity is stamped. None of that is restated here. What this rule adds is the part that decides where the boundary is drawn rather than what sits inside it once drawn, and the fact the boundary emits when it moves.

**Events are in this rule because an event is what crosses an aggregate boundary.** Conditions 1 to 4 say a boundary is a consistency boundary and that nothing spans two of them synchronously. That immediately raises the question of how the second aggregate ever learns, and the answer is a fact published by the first. Split across two rules, the boundary conditions get adopted and the second aggregate is updated by a second repository call in the same transaction, which is condition 2 violated in the name of satisfying condition 4. The subject is one subject, for the same reason `rules/value-semantics.md` gives about its own two halves. `docs/contract-first.md` owns the event's shape on the wire; this rule owns its shape in the model, and the two do not overlap.

No condition here adds an abstraction. An invariant moved inside a boundary, a reference replaced by an identifier and an entity replaced by the identity of one are each smaller than the state they replace, so the abstraction trigger in condition 1 of `rules/yagni.md` gates none of them. Condition 4 is the one that looks like it should: making consistency eventual usually introduces a publisher and a handler. It is not gated either, and the reason is in the boundary section below.

## Conditions

1. **An invariant that must hold at every commit lies inside one aggregate.** The state is a rule the business states as always true whose terms reach two roots. The boundary is drawn by the invariants and not by the object graph, which is Evans' definition in *Domain-Driven Design*, and it is the condition the other three aggregate conditions follow from: a boundary drawn anywhere else makes conditions 2 and 3 arbitrary. There is no threshold; the invariants either partition over the roots or they do not. Decided by a reviewer listing the invariants and the roots each one names.

2. **A transaction modifies one aggregate root.** The state is a use case that loads two roots and writes both inside one unit of work. The number is one, it is Vernon's rule from *Effective Aggregate Design*, and the argument is not taste: a transaction's contention is set by the union of what it writes, so two roots per transaction makes the conflict rate a product of two aggregates' write rates rather than a sum, and the boundary the model declared is not the boundary the database is enforcing. Creating a root and then modifying it is one root. Reading a second root is not modifying it. Decided by a reviewer reading the use case, or by a script once the project names the base type its repositories inherit — the same input condition 3 of `rules/domain-model.md` already asks for.

3. **An aggregate refers to another aggregate by identity.** The state is a field, anywhere inside one aggregate, whose declared type is another aggregate's root. Vernon's third rule, and it is a condition rather than a preference because a direct reference breaks condition 2 silently: nothing at the call site says that reaching through the field has crossed into another consistency boundary, so the second root gets modified by a caller who did not know there was a second root. The identifier is the other root's identifier type rather than a bare string, so the reference still says what it points at. Decided by a reviewer, or by a script given the root marker.

4. **Consistency across a boundary is eventual, and the gap has an owner, a window and a repair.** The state is a use case that requires two roots to agree by the time it returns. Vernon's fourth rule. What the condition requires is not a particular mechanism but three answers: which root is authoritative, how long the other may disagree, and what closes the gap when the first attempt does not. The window is a figure and this plugin does not supply it, because it is set by what the business can tolerate rather than by anything here — the same position condition 4 of `rules/cross-cutting-concerns.md` takes about an idempotency retention window and condition 6 of `rules/solid.md` takes about the layer map. What is not acceptable is the window being unstated, because an unstated window is one nobody is monitoring. Decided by a reviewer against a figure the project states.

5. **A domain event carries the identity of the aggregate it happened to and the time it happened.** Two fields, and the number is argued rather than chosen. An event's type name already says what happened; a consumer holding the event still cannot act without knowing which instance it happened to and when, and no other question is asked of every event. A third field naming the actor is the one usually proposed and it is not in the set, because who acted is already on the aggregate's audit stamp, which condition 3 of `rules/domain-model.md` requires — putting it on the event as well creates two answers that can disagree. Everything beyond the two is the event's own payload and varies per event. Decided by a reviewer, or by a script given the event marker.

6. **A domain event is immutable and carries no entity.** Two states: an event type that is not declared immutable, and an event field whose declared type is an entity or an aggregate root rather than an identifier or a value. An event is a fact about the past, so a mutable one is a fact that can be edited after it was recorded, and an event carrying an entity hands a consumer a live object whose state has moved on since the fact was true. The immutability half is decided by conditions 3 and 4 of `rules/value-semantics.md`, which `hooks/check-structure.py` already runs over any type declared frozen; the declaration itself and the no-entity state are decided by a reviewer, or by a script given the event marker.

## Where this stops

**Condition 1 does not say the boundary is small.** Small aggregates are the usual advice and they are a consequence rather than a rule: a boundary drawn around exactly the invariants that must hold is usually small, and one that is large because the invariants are genuinely large is correct. A boundary shrunk below its invariants has not removed the invariant, it has moved the enforcement into the application layer where nothing guarantees it, which is the more common defect and the one this condition is aimed at. `docs/aggregates.md` works the trade through.

**Condition 2 does not reach a batch, a migration or a repair job.** Work whose subject is many roots at once — a backfill, a bulk reprice, an import — touches many by definition, and requiring one per transaction there means either one transaction per root, which is usually right, or an argument that the job is not a use case. The condition is about the operations a user triggers, where the transaction is the unit of intent.

**Condition 2 does not reach a root created and used in the same unit of work.** A use case that creates an order and its first payment where payment is a separate root is writing two roots, and if the second cannot exist without the first, the two are one invariant and condition 1 says so. The fix is the boundary, not a second transaction, and the condition read on its own would send an author to the wrong one.

**Condition 3 does not reach a read model.** A projection, a query result and a view assembled for a screen hold whatever their consumer needs, including several roots at once, and copying an identifier into them so they can be re-resolved is ceremony with no invariant behind it. The condition binds the model that enforces rules, not the shapes derived from it — the same distinction condition 3 of `rules/domain-model.md` makes when it declines to require the audit stamp on everything derived from a record.

**Condition 4 is not gated by the abstraction trigger, and that needs saying because it looks gated.** Making consistency eventual usually introduces a publisher, a handler and a queue, which is exactly the kind of structure `rules/yagni.md` deletes when it has one consumer. The reason the trigger does not reach it is the one `docs/simplicity.md` gives for the SOLID conditions that remove structure: the condition does not ask for the machinery, it forbids a synchronous write to two roots. The smallest fix is to move the boundary so there is one root, and that is a removal. Where the boundary genuinely cannot move, the machinery arrives with the second root as its second consumer, so the trigger is satisfied before it is consulted.

**Condition 4 does not reach two roots that never need to agree.** Eventual consistency is a statement about a gap that matters. Two aggregates with no invariant between them have no gap, and writing down a window for one is process without a subject. The test is whether anybody would file a defect if the two disagreed forever.

**Condition 5 does not settle the event's name, and the suffix test was considered and refused.** An event is named for a fact in the past and the mistake that happens is a command wearing an event's clothes: `SendInvoice` published as an event, so that the handler is not reacting to something that happened but obeying something that was asked. `rules/naming.md` in the foundation plugin has a precedent for catching exactly this class of mistake cheaply — its skill names are checked by a suffix test for `ing` — and the equivalent here fails, because English past participles are irregular where gerunds are not. A test for a trailing `ed` rejects `OrderPaid`, `PaymentSent`, `FundsWithdrawn` and `InvoiceIssued`, which are the correctly named ones. A detector that is wrong about correct code teaches people to switch the gate off, and `docs/simplicity.md` records the condition this plugin already deleted for that. So the name is a reviewer's call, and the question to ask is whether the sentence "this has happened" can be said of the type without embarrassment.

**Condition 6 does not reach what the event means.** An event carrying the right fields, immutable, named in the past tense, can still record a fact the business does not recognise — a row changing rather than something happening. That is the same defect `docs/bounded-contexts.md` describes for an anaemic domain type and it has the same test: read it back to someone who does this work and see whether they recognise the fact.

**Nothing here covers the rest of the tactical vocabulary.** Specification, factory, domain service and the modelling half of value object are absent. The mechanical half of value object is in `rules/value-semantics.md` and the entity contract is in `rules/domain-model.md`; the others have no artifact and their absence means this plugin has nothing useful to say about them yet, not that they are wrong. `docs/patterns.md` records the same kind of scope for its own catalog.

**This rule declares judgment rather than a hook, and the route was not available.** `enforced-by` names a script that decides the rule's conditions, and no such script can exist here without an input this plugin cannot guess. Every detector above is real and runnable — a use case's writes are countable, a field's declared type is readable, two required fields are a set difference — and every one of them first has to be told which type is an aggregate root, which is an event, and which function is a use case. A hook that guessed those would have to hard-code a base-type name or a directory, and the first project arranged differently would get a gate that is confidently wrong, which is the failure `docs/simplicity.md` records and which already cost `rules/kiss.md` a condition. The search for a parser-decidable fragment turned up only the immutability half of condition 6, and `hooks/check-structure.py` already decides that under `rules/value-semantics.md`, so there is nothing new to point at. This is `rules/contract-first.md`'s position exactly: runnable detectors, project-supplied inputs, judgment declared and the detectors named as jobs the consuming project wires in. It is not `rules/solid.md`'s case, where a script exists and would deliver two of six conditions, and it is not `rules/value-semantics.md`'s, where a parser decides everything and the gating fits in a finding message.

**The footprint is the cost, and it is 154 characters.** A judgment rule's `statement` is injected into every request, including the ones with no domain model in them, and this plugin was carrying 847 characters across six such rules before this one — up from 281 across two, as `docs/context-budget.md` in the foundation plugin accounts for. Seven rules and 1,001 characters is the number a reviewer should weigh against what the rule delivers, and the honest summary is that the alternative was not a cheaper enforcement route but no rule at all. `rules/duplication.md` went the other way for the opposite reason, and its final section sets out that trade.
